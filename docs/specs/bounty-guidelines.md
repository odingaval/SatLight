# Bounty Guidelines

## What makes a good bounty
- One clear outcome that can be reviewed in under an hour.
- Link to a GitHub issue with context, files to touch, and acceptance criteria.
- A fair reward for the effort. Guideline ranges: Trivial 500-2,000 sats, Easy 2,000-10,000, Medium 10,000-50,000, Hard above 50,000.
- Realistic expiry (default 90 days).

## Allowed
Docs, translations, bug fixes, tests, small features, code reviews, accessibility fixes, dependency updates.

## Not allowed
- Bounties on work that violates the law, a license, or GitHub terms
- Malware, exploit development, or harassment tooling
- Self-dealing (paying your own accounts)
- Requests for personal data or private keys
- Bounties without a verifiable GitHub issue

## Maintainer responsibilities
- Review PRs promptly (target 7 days). Reject with reasons.
- Do not move goalposts after a claim.
- Merge good work: the payout follows the merge.

## Contributor responsibilities
- Claim only what you can finish; release otherwise.
- Follow the repo's contributing guide and license.
- Do not submit AI-generated or copied code you cannot license or explain.
- One PR per bounty, referencing `Closes #N`.

## Security reports
Vulnerability bounties follow `SECURITY.md`, not public issues.
